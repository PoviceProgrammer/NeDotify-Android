3. Текущие дефекты первого этапа
P1-1. TTL подписанного SoundCloud URL берётся не из того параметра — кэш отдаёт мёртвые ссылки ~2 часа
Файл: app/src/main/java/ru/nedotify/app/data/Sources.kt:46-49 (streamExpiry), применяется в Sources.kt:92 и Sources.kt:136.

return (values["expire"]?:values["expires"])?.toLongOrNull()?.let { it*1000-60_000 }
    ?: (now+15*60_000)
Сценарий (воспроизведён на живых данных 2026-10-18). Реальный URL, выданный /media/.../stream/hls:

https://playback.media-streaming.soundcloud.cloud/…/playlist.m3u8
  ?expires=1792322643                (11:24 UTC)
  &Policy=<base64, DateLessThan."AWS:EpochTime" = 1792315369>   (09:22 UTC)
  &Signature=…&Key-Pair-Id=…
streamExpiry читает только expires и вычитает 60 с → кэш живёт до 1792322583 (11:23 UTC). CloudFront отвергнет подпись с 1792315369 (09:22 UTC). Окно, в котором StreamCache (ёмкость 128) отдаёт заведомо мёртвый URL: 7 214 с ≈ 120 минут. Сравнение expires и Policy.expires (1 792 322 449) тоже различается — брать надо минимум.

Последствие. Через ~2 ч работы приложения ранее разрешённые SoundCloud-треки начинают отдавать 403. Спасает только ограниченный одноразовый retry (PlaybackService.kt:106-122), но он тратит отдельный round-trip и даёт заметный stall, а retryCount>=1 закрывает повтор. В очереди из нескольких треков подряд получится каскад пауз, а на повторном 403 — «мёртвая» ошибка без причины.

Исправление. Разбирать Policy (URL-unescape → base64url с заменой ~ на =) и брать min(expires, Statement[0].Condition.DateLessThan["AWS:EpochTime"]) * 1000 - 60_000. Запас в 60 с применять и к ветке по умолчанию (now+15 мин), а не только к распознанному expires. Покрыть тестом SoundCloud URL с CloudFront Policy.

P2-7. Резолвер URL блокирует поток загрузчика Media3 на всё время сетевого запроса
Файл: app/src/main/java/ru/nedotify/app/player/PlaybackService.kt:52-57

ResolvingDataSource.Resolver по контракту синхронный, и Media3 вызывает его на своём пуле загрузки размером min(4, max(1, cpu/2)). 5. API 26 и API 37 — отдельно

Найденное поведение на 26–32: FGS без типа (атрибут API 29+ игнорируется) — работает; POST_NOTIFICATIONS не существует — дефекта P2-3 на этой версии нет; java.time доступен ровно с 26. Инструментально не проверено — устройства нет.

API 37 (target/compile, Android 17). Подтверждено инструментально: compileSdkVersion=37, targetSdkVersion=37, platformBuildVersionName='17' (из APK). Сборка и линт проходят под SDK 37.

Не проверено и не утверждается: поведение на реальном устройстве/эмуляторе API 37 — foreground-service/media-session поведение, декодирование, перемотка, HLS-воспроизведение, возобновление после перезагрузки процесса. Для этого нужен либо физический телефон, либо работающий эмулятор; см. раздел 2.8 — ни то, ни другое на этой машине недоступно (драйвер гипервизора не установлен, его установка запрещена). Любые утверждения о поведении API 37 без устройства были бы догадкой, поэтому их в отчёте нет.
